# Work Item DAG & Scheduler — Design Document

**Date**: 2026-02-26
**Author**: Subhagato
**Status**: Draft
**Refines**: FR-005 (Work Item System), Phase 3 (Work Item DAG + Scheduler)

---

## 1. Overview

This document specifies the architecture of Slate Agent's Work Item system — the data model, DAG construction, state machine, Tokio task integration, artifact storage, budget enforcement, and concurrency model. Work Items are the unit of agent work: each represents a discrete goal with acceptance criteria, inputs, outputs, and budget constraints. Work Items form a directed acyclic graph (DAG) expressing execution dependencies, and the Tokio runtime executes them concurrently where the graph permits.

The PRD (FR-005, Phase 3) defines Work Items at a requirements level. This design provides the concrete implementation.

## 2. Problem

The PRD defines Work Items and DAG scheduling at a high level — goals, acceptance criteria, dependencies, states, and concurrent execution. It does not specify:

- The exact data model with all fields, types, and constraints
- How DAGs are constructed from agent (TeamLead) structured output and validated
- How Tokio (the Rust async runtime) is integrated — the mapping from Work Item DAG to Tokio tasks
- The full state machine with all transitions and their triggers
- How artifacts are stored, typed, and referenced
- How budget enforcement works in practice — warning thresholds, pause mechanics, escalation flow
- The concurrency model — what is shared, what is isolated, how many can run simultaneously

This design fills those gaps.

## 3. Work Item Data Model

```rust
struct WorkItem {
    // Identity
    id: String,                          // UUID v4, generated by daemon
    parent_id: String,                   // Parent Work Item ID (for recursive decomposition), empty if root

    // Task definition
    goal: String,                        // Natural language: what this Work Item must accomplish
    acceptance_criteria: Vec<String>,    // Conditions for completion
    risk_level: RiskLevel,               // low | medium | high | critical

    // Assignment
    assigned_role: AgentRole,            // Orchestrator | TeamLead | Engineer | Reviewer | Researcher | Security | Perf
    model_id: String,                    // Model from catalog (e.g., "claude-sonnet-4-5")
    assigned_agent_session_id: String,   // Set when a running agent picks this up, empty until then

    // State
    state: WorkItemState,                // pending | running | completed | failed | blocked | cancelled
    dependencies: Vec<String>,           // Work Item IDs that must complete before this starts

    // Budget
    token_budget: u64,                   // Maximum tokens across all LLM calls
    cost_budget_cents: u64,              // Maximum cost in cents (integer to avoid float precision)
    tokens_used: u64,                    // Running total, updated by aisdk.rs usage callbacks
    cost_used_cents: u64,                // Running total, calculated from tokens_used × model rate

    // Inputs
    inputs: WorkItemInputs,

    // Outputs
    outputs: WorkItemOutputs,

    // Timestamps
    created_at: String,                  // ISO 8601
    started_at: Option<String>,          // Set on transition to running
    completed_at: Option<String>,        // Set on transition to completed/failed
}

struct WorkItemInputs {
    repo_path: String,                   // Repository root path
    cwd: String,                         // Working directory for this Work Item
    tool_allowlist: Option<Vec<String>>, // Restrict available tools (None = all)
    env_snapshot_id: String,             // Reference to the env snapshot to initialize the worker bash
    context: String,                     // Additional context from parent (TeamLead's notes, prior artifacts)
}

struct WorkItemOutputs {
    artifact_ids: Vec<String>,           // IDs of artifacts produced
    summary: String,                     // One-line summary of what was accomplished
    error: Option<String>,               // Error description if state is failed
}
```

### Enumerations

```rust
enum WorkItemState {
    Pending,     // Waiting for dependencies or scheduler
    Running,     // Agent session active, executing
    Completed,   // Agent reported success, outputs stored
    Failed,      // Agent reported failure, or budget/timeout exceeded
    Blocked,     // A dependency has failed
    Cancelled,   // Parent task cancelled, or user cancelled
}

enum AgentRole {
    Orchestrator,
    TeamLead,
    Engineer,
    Reviewer,
    Researcher,
    Security,
    Perf,
}

enum RiskLevel {
    Low,
    Medium,
    High,
    Critical,
}
```

### Storage

Work Items are stored in-memory during a session and persisted to disk as JSON at `~/.slate-agent/state/<session_id>/work_items.json`. Persistence enables session recovery if the daemon restarts.

## 4. State Machine

### State Transition Diagram

```
                ┌──────────┐
     ┌──────────│ Cancelled │
     │          └──────────┘
     │                ▲
     │                │ parent cancelled / user cancel
     │                │
     │          ┌─────┴────┐
     │    ┌─────│  Pending  │◄────────────────┐
     │    │     └─────┬────┘                  │
     │    │           │                       │
     │    │           │ all deps completed    │ TeamLead retries
     │    │           │ + scheduler picks up  │ (creates new Work Item)
     │    │           ▼                       │
     │    │     ┌──────────┐                  │
     │    │     │ Running  │──────────────────┘
     │    │     └────┬─────┘
     │    │          │
     │    │     ┌────┴──────┐
     │    │     │           │
     │    │     ▼           ▼
     │    │ ┌──────────┐ ┌────────┐
     │    │ │Completed │ │ Failed │
     │    │ └──────────┘ └────────┘
     │    │
     │    │ dependency failed
     │    ▼
     │ ┌─────────┐
     └─│ Blocked │
       └─────────┘
```

### Transition Table

| From | To | Trigger | Action |
|------|----|---------|--------|
| `Pending` | `Running` | All dependencies in `Completed` state AND scheduler thread available | Set `started_at`; spawn agent session; assign `assigned_agent_session_id` |
| `Pending` | `Blocked` | Any dependency transitions to `Failed` | Log blocked reason; notify TeamLead |
| `Pending` | `Cancelled` | Parent Work Item cancelled OR user issues cancel command | Set `completed_at`; propagate cancellation to child Work Items |
| `Running` | `Completed` | Agent reports success; all acceptance criteria met (or Reviewer approves) | Set `completed_at`; store artifacts; update `outputs`; destroy agent session; trigger Narrator |
| `Running` | `Failed` | Agent reports failure OR tool error OR budget exceeded (100%) OR timeout (configurable, default 30 min) | Set `completed_at`; store partial artifacts + error; destroy agent session; notify TeamLead |
| `Blocked` | `Pending` | TeamLead resolves the blocking failure (creates fix Work Item that completes successfully) | Reset to pending; re-evaluate dependencies |
| `Cancelled` | — | Terminal state | No transitions out |
| `Completed` | — | Terminal state | No transitions out |

### Atomicity

State transitions are protected by a mutex in the daemon's WorkItemManager. Each transition:

1. Acquires the lock
2. Validates the transition is legal (check current state and trigger condition)
3. Updates the state and timestamps
4. Persists the updated Work Item to disk
5. Fires any downstream effects (unblock dependents, notify TeamLead, trigger Narrator)
6. Releases the lock

Transitions are logged to the session's metrics file with timestamps for debugging and analytics.

## 5. DAG Construction

### 5.1 TeamLead Produces the Plan

The TeamLead receives a task description from the Orchestrator and produces a structured JSON plan. The daemon parses this into Work Items:

```json
{
  "work_items": [
    {
      "id": "temp-1",
      "goal": "Refactor auth.cpp to use JWT library",
      "acceptance_criteria": [
        "jwt-cpp library integrated via CMakeLists.txt",
        "Session cookie logic replaced with JWT validation",
        "Existing tests still pass"
      ],
      "assigned_role": "Engineer",
      "model_id": "claude-sonnet-4-5",
      "risk_level": "medium",
      "token_budget": 50000,
      "cost_budget_cents": 25,
      "dependencies": [],
      "context": "Current auth is in auth.cpp using session cookies stored in Redis."
    },
    {
      "id": "temp-2",
      "goal": "Write unit tests for JWT validation",
      "acceptance_criteria": [
        "Tests cover valid tokens, expired tokens, malformed tokens",
        "Tests cover missing Authorization header",
        "All tests pass with make test"
      ],
      "assigned_role": "Engineer",
      "model_id": "gemini-2.5-flash",
      "risk_level": "low",
      "token_budget": 20000,
      "cost_budget_cents": 5,
      "dependencies": ["temp-1"],
      "context": "Tests should go in test/auth_test.cpp. Use GoogleTest framework."
    },
    {
      "id": "temp-3",
      "goal": "Security review of JWT implementation",
      "acceptance_criteria": [
        "No hardcoded secrets or keys",
        "Token expiry is enforced (not just checked)",
        "Algorithm is explicitly set (not 'none')",
        "Token validation happens before any data access"
      ],
      "assigned_role": "Security",
      "model_id": "claude-opus-4",
      "risk_level": "high",
      "token_budget": 30000,
      "cost_budget_cents": 50,
      "dependencies": ["temp-1"],
      "context": "Focus on OWASP JWT best practices. Check for JWT confusion attacks."
    }
  ]
}
```

### 5.2 Validation

The daemon validates the TeamLead's plan before constructing the DAG:

1. **Cycle detection**: Perform topological sort on the dependency graph. If a cycle is detected, reject the plan and ask the TeamLead to fix it.
2. **Dependency existence**: Every ID in `dependencies` must reference another Work Item in the same plan (using temp IDs) or an existing Work Item in the session.
3. **Role validation**: `assigned_role` must be a valid role enum value.
4. **Model validation**: `model_id` must exist in the model catalog.
5. **Budget validation**: `token_budget` and `cost_budget_cents` must be > 0 and within the session-level budget (if configured).

If validation fails, the daemon injects an error message into the TeamLead's context describing the specific validation failure, and the TeamLead is asked to revise.

After validation, temp IDs are replaced with real UUIDs.

### 5.3 Dynamic DAG Modification

The DAG is not static — it can be modified at runtime:

- **Reviewer creates fix Work Items**: When a Reviewer rejects a Work Item, it produces fix suggestions. The daemon creates a new fix Work Item with the Reviewer's feedback as context, adds it to the DAG with the rejected Work Item's dependencies, and re-adds a Reviewer Work Item dependent on the fix.
- **TeamLead adds Work Items**: If a running Work Item discovers unexpected complexity, the TeamLead can add new Work Items to the DAG at runtime.
- **User cancels a subtree**: The user can cancel a Work Item, which cascades `Cancelled` to all its dependents.

Dynamic modifications are applied atomically — the scheduler pauses briefly while the DAG is updated, then resumes with the new graph.

### 5.4 DAG Visualization

The DAG tree is rendered in slate's task header block, updated live as Work Items change state:

```
Task: Refactor auth module to use JWT
├── ● Refactor auth.cpp to use JWT library          [Engineer, claude-sonnet-4-5]
├── ○ Write unit tests for JWT validation            [Engineer, gemini-2.5-flash]  ← depends on ●
└── ○ Security review of JWT implementation          [Security, claude-opus-4]     ← depends on ●
```

Status indicators:
- `●` running (with elapsed time)
- `◐` in review (Reviewer active)
- `○` pending (waiting for dependencies)
- `✓` completed
- `✗` failed
- `⊘` cancelled
- `◫` blocked

The task header auto-updates in place (ratatui redraws the widget). Each Work Item line shows the assigned role and model.

## 6. Tokio Integration

### 6.1 Mapping Work Items to Tokio Tasks

The daemon maps the Work Item DAG to Tokio tasks:

```rust
let semaphore = Arc::new(Semaphore::new(max_concurrent_workers)); // default: 4
let mut handles = Vec::new();

// Spawn tasks respecting dependencies
for work_item in ready_work_items(&dag) {
    let permit = semaphore.clone().acquire_owned().await?;
    let handle = tokio::spawn(async move {
        execute_work_item(&work_item).await;
        drop(permit);
    });
    handles.push(handle);
}

futures::future::join_all(handles).await;
```

### 6.2 Work Item Execution

When a Tokio task runs, `execute_work_item()`:

1. Transitions the Work Item to `Running`
2. Spawns a worker bash process in slated (initialized from env snapshot)
3. Creates an AgentSession with the Work Item's assigned model and role-specific system prompt
4. Runs the agent tool calling loop (see agent-system-design.md, Section 3.2)
5. On completion: stores artifacts, transitions to `Completed` or `Failed`
6. Destroys the agent session and kills the worker bash process

### 6.3 Conditional Task Flow for Reviewer Flow

Conditional task flow handles the Reviewer's approve/reject decision:

```rust
loop {
    execute_work_item(&engineer_wi).await;
    execute_work_item(&reviewer_wi).await;

    match reviewer_wi.outputs.summary.as_str() {
        "approve" => break,
        _ => {
            // Create fix Work Item, add to DAG
            create_fix_work_item(&engineer_wi, &reviewer_wi.outputs).await;
            // Loop back to re-execute
        }
    }
}
// All done — mark parent task complete
```

### 6.4 Dynamic Graph Modification

When new Work Items are added at runtime (fix items from Reviewer, additional items from TeamLead):

1. The daemon signals the scheduler to pause (no new tasks fire)
2. Updates the DAG state with the new Work Items and their dependencies
3. Resumes execution — new tasks are spawned into the Tokio runtime as dependencies resolve

Dynamic modification is handled by updating the DAG state and spawning new tasks. The Tokio runtime naturally supports this: new tasks can be spawned at any time, and dependency tracking is managed by the daemon's scheduler layer rather than the runtime itself.

## 7. Artifact Storage

### 7.1 Storage Layout

```
~/.slate-agent/state/<session_id>/
├── work_items.json                    # All Work Items for this session
└── artifacts/
    └── <work_item_id>/
        ├── manifest.json              # Artifact metadata index
        ├── diff_001.patch             # Unified diff
        ├── log_001.txt                # Command transcript
        ├── file_auth.cpp              # Created/modified file snapshot
        ├── test_report_001.json       # Test results
        └── summary.md                 # Human-readable summary
```

### 7.2 Artifact Types

| Type | Extension | Description | Written By |
|------|-----------|-------------|------------|
| `diff` | `.patch` | Unified diff of file changes | Engineer (after Edit/Write tool) |
| `log` | `.txt` | Command transcript (stdin + stdout + stderr + exit codes) | Daemon (from worker bash session) |
| `file` | Original extension | Snapshot of created or significantly modified file | Engineer (after Write tool) |
| `test_report` | `.json` | Structured test results (pass/fail counts, failures) | Engineer (after running tests) |
| `summary` | `.md` | Human-readable summary of what was accomplished | Agent (on Work Item completion) |
| `review` | `.json` | Reviewer's verdict and criterion results | Reviewer (on review completion) |

### 7.3 Artifact Manifest

Each Work Item's artifact directory contains a `manifest.json`:

```json
{
  "work_item_id": "a1b2c3d4-...",
  "artifacts": [
    {
      "id": "art-001",
      "type": "diff",
      "filename": "diff_001.patch",
      "created_at": "2026-02-26T14:30:00Z",
      "size_bytes": 1523,
      "description": "Changes to auth.cpp: replaced session cookie with JWT validation"
    },
    {
      "id": "art-002",
      "type": "log",
      "filename": "log_001.txt",
      "created_at": "2026-02-26T14:30:15Z",
      "size_bytes": 4201,
      "description": "Build and test transcript"
    }
  ]
}
```

Artifacts are referenced by ID in Work Item outputs and in Shared Project State. The Reviewer reads artifacts by ID to validate the Engineer's work.

### 7.4 Cleanup

Session artifacts are deleted after a configurable retention period:

```toml
# ~/.slate-agent/config.toml
[state]
retention_days = 7          # Delete session state older than this
max_state_size_mb = 500     # If total state exceeds this, delete oldest sessions first
```

Cleanup runs on daemon startup and periodically (every 24 hours while the daemon is running).

## 8. Budget Enforcement

### 8.1 Token Tracking

Token usage is tracked per Work Item via aisdk.rs's usage callbacks:

```rust
// aisdk.rs reports usage after each completion call
fn on_usage(&mut self, prompt_tokens: u64, completion_tokens: u64) {
    let total = prompt_tokens + completion_tokens;
    self.work_item.tokens_used += total;

    let model = self.catalog.get(&self.work_item.model_id);
    let cost_cents = (prompt_tokens * model.input_cost_per_million / 1_000_000)
                    + (completion_tokens * model.output_cost_per_million / 1_000_000);
    self.work_item.cost_used_cents += cost_cents;

    self.check_budget(&self.work_item);
}
```

### 8.2 Enforcement Thresholds

| Threshold | Action |
|-----------|--------|
| 80% of token or cost budget | **Warning**: Inject a message into the agent's context: `[BUDGET WARNING: You have used 80% of your token budget. Complete the task efficiently.]` |
| 100% of token or cost budget | **Pause**: Stop the current LLM call. Do not make further API calls for this Work Item. Transition to `Failed` with error: `budget_exceeded`. |

### 8.3 Escalation

When a Work Item fails due to budget:

1. The daemon notifies the TeamLead (or Orchestrator if no TeamLead) with the failure details
2. The TeamLead can:
   a. **Split**: Decompose the remaining work into smaller Work Items with their own budgets
   b. **Downgrade**: Re-assign with a cheaper model (lower cost-per-token)
   c. **Increase budget**: Request user approval for a budget increase (confirmation prompt in slate)
   d. **Fail**: Accept the failure and report to the user

### 8.4 Session-Level Budget

An optional session-level budget caps total spending across all Work Items:

```toml
# ~/.slate-agent/config.toml
[budget]
session_token_limit = 1000000       # Max tokens per session
session_cost_limit_cents = 500      # Max cost per session ($5.00)
```

When the session budget is reached, no new Work Items are scheduled. Running Work Items are allowed to complete (killing them mid-execution wastes the tokens already spent).

## 9. Concurrency Model

### 9.1 Isolation Guarantees

Each running Work Item is fully isolated:

| Resource | Isolation |
|----------|-----------|
| LLM session | Own `AgentSession` with own conversation history and system prompt |
| Bash process | Own worker bash process, spawned by slated from env snapshot |
| Artifact directory | Own directory at `artifacts/<work_item_id>/` |
| File write ownership | Single-writer — daemon tracks which Work Item owns writes to which files |
| Environment | Initialized from env snapshot at spawn time; changes do not propagate to other Work Items |

### 9.2 No Shared Mutable State

Concurrent Work Items share no mutable state:

- **File system**: Single-writer ownership ensures at most one Work Item writes to any given file. If two Work Items need the same file, they must be sequential (expressed as a dependency in the DAG).
- **Memory**: Each agent session has its own conversation history. Project memory (project.md) is read-only during execution — only the Narrator writes to it, and only after Work Items complete.
- **Env snapshot**: Each Work Item's bash process is initialized from the snapshot captured at the time the session started (or last refreshed). Running Work Items do not see each other's environment changes.

### 9.3 Concurrency Limits

```toml
# ~/.slate-agent/config.toml
[scheduler]
max_concurrent_work_items = 4       # Matches default Tokio concurrent task limit
```

The Tokio semaphore permit count is set to `max_concurrent_work_items`. When all permits are held, additional ready Work Items wait for a semaphore permit until one becomes available.

Factors for choosing the default of 4:
- Each running Work Item holds an LLM connection (HTTP keep-alive) — too many saturates network bandwidth
- Each running Work Item holds a worker bash process — too many consumes PIDs and memory
- Most DAGs have 2-4 independent branches — 4 threads covers the common case
- User can increase for larger DAGs on powerful machines

### 9.4 File Write Ownership

The daemon maintains an ownership table:

```rust
// key: absolute file path
// value: Work Item ID that holds write ownership
let file_ownership: Arc<Mutex<HashMap<String, String>>> = Arc::new(Mutex::new(HashMap::new()));

fn acquire_write(
    file_ownership: &Mutex<HashMap<String, String>>,
    file_path: &str,
    work_item_id: &str,
) -> bool {
    let mut map = file_ownership.lock().unwrap();
    match map.get(file_path) {
        None => {
            map.insert(file_path.to_string(), work_item_id.to_string());
            true  // ownership acquired
        }
        Some(owner) if owner == work_item_id => true,
        Some(_) => false,  // another Work Item owns this file
    }
}
```

When an Engineer's Write or Edit tool call targets a file:
1. The daemon checks ownership before executing the tool
2. If owned by another Work Item, the tool call returns an error: `"File {path} is currently owned by Work Item {id}. Cannot write."`
3. The agent sees the error and can either wait (by re-trying later) or report it as a blocker

Ownership is released when the owning Work Item transitions to `Completed`, `Failed`, or `Cancelled`.

## 10. Open Questions

1. **Partial completion (checkpoint + resume)**: Should Work Items support saving a checkpoint (conversation history + partial artifacts) so they can be resumed after a daemon restart? Currently, a daemon restart loses all in-flight Work Items. Checkpointing adds complexity but improves resilience for long-running tasks.

2. **DAG re-planning on new user input**: If the user provides new input while a DAG is executing (e.g., "also add rate limiting"), how should the system handle it? Options: (a) cancel the current DAG and re-plan from scratch, (b) have the TeamLead produce an additive modification to the existing DAG, (c) queue the new input until the current DAG completes.

3. **Content-addressable artifact storage**: Should artifacts use content-addressable hashing (SHA-256 of content as filename) for deduplication? This would save disk space when multiple Work Items produce similar artifacts (e.g., same file read by multiple reviewers). Adds complexity and may not be worth it given the 7-day default retention.

4. **Work Item priority**: The current design treats all ready Work Items equally — the Tokio scheduler picks them in arbitrary order. Should Work Items support a priority field so that critical-path items execute first when worker threads are limited?

5. **Cross-session Work Item references**: Should Work Items be able to reference artifacts from previous sessions? This would enable incremental workflows ("continue where we left off"), but requires extending artifact retention and adding a cross-session lookup mechanism.
